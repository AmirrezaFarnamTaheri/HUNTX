# HuntX Repository Audit & Remediation — 2026-07-26

Branch: `claude/repo-audit-optimization-2y7erg` · Base: `main@4da38fa`

This document records a multi-pass audit of the HuntX codebase and the concrete,
behavior-preserving remediations applied in this branch. Every change described
here is committed and verified at the branch tip: **357 tests pass**, the
CI-gated lint selection is clean, there are no unused imports, and `mypy`
reports no issues across all 76 source files (see §6 for the full matrix).

The guiding principle for remediation was *fix what is provably correct and
low-risk; document what carries behavior risk*. Findings that would change
runtime semantics of the ingestion/publish pipeline in ways a maintainer should
sign off on are listed in [Section 4](#4-known-risks-documented-not-changed)
rather than silently altered.

   selected raw blobs for deletion without the active-record guard its sibling
   `get_processed_hashes` already applies, so a blob still referenced by a live
   blob-dependent record could be unlinked from disk, corrupting the next route
   build irrecoverably. **Fixed** — see §3.5.
1. **CI was red on `main`.** Commit `4da38fa` loosened config validation to

3. **`RawStore.get`/`exists` built filesystem paths from an unvalidated hash.**
   **Fixed** (hex validation) — §3.2.
4. **Hardened publish stage could abort the whole run** on a single malformed

5. **Published dev outputs were written non-atomically** while the manifest was

## 2. Module-by-module audit

### `config/`
- `env_expand.py`: `${VAR}` (unset, no default) silently expanded to `""`,
  masking misconfiguration. `config.prod.yaml` uses bare `${TELEGRAM_API_ID}`
  etc., so a production deploy missing those vars would proceed with empty
  credentials. **Fixed** to fail loud; `${VAR:-default}` remains the sanctioned
  optional/dev escape hatch.
- `schema.py`: `validate_api_id` swallowed non-numeric input (e.g. a typo or an
  unexpanded `${...}`) as `None`. **Fixed** to raise on genuine garbage while
  still treating absent/empty/zero as an optional `None`.
- `validate.py`: sound layered validation with a `HUNTX_STRICT`/`CI` gate for
  credential strictness. No change needed.

### `store/` and `state/`
- `rejects.py`: import-time default-argument path binding. **Fixed** to resolve
  `paths.REJECTS_DIR` at runtime, matching `RawStore`/`ArtifactStore`.
- `raw_store.py`: `get`/`exists` now reject any value that is not a 64-char
  lowercase hex digest before path construction. **Fixed.**
- `artifact_store.py`: already performs `resolve()` + `is_relative_to` traversal
  defense — verified clean.
- `state/repo.py`, `state/ingestion_queue.py`: SQL is consistently parameterized;
  f-strings only interpolate `?`-placeholder counts / validated ints. `db.py`
  applies WAL/busy-timeout PRAGMAs and commits/rolls back/closes correctly.
  Clean on injection and connection handling — but the deeper pass found a
  **CRITICAL** blob-prune data-loss bug in `repo.prune_old_data` (**fixed**,
  §3.5) plus several open data-integrity items (§4.5).

### `core/`
- `hardened_orchestrator.py`: unguarded `build_result["route_name"]` subscript in
  the publish loop. **Fixed** to skip non-dict results and use `.get`, matching
  the base `Orchestrator`.
- `orchestrator.py`: three published dev-output files written with plain
  `write_text` while the manifest used `atomic_write`. **Fixed** to use
  `atomic_write` for all four.
- `session_lease.py` TOCTOU and deprecated `get_event_loop()` usage: **both
  fixed** in later passes (§3.5). `hardened_orchestrator.py` thread-pool
  shutdown remains open (§4.1).

### `connectors/`
- `base.py` / `telegram_user/connector.py`: sync wrappers used deprecated
  `asyncio.get_event_loop()` + `run_until_complete` without an `is_running`
  check; `__del__` triggered network cleanup during GC. **Both fixed** — see
  §3.5 (`run_sync` migration, I/O-free `__del__`).
- Download size caps relied on self-reported `file_size` metadata before an
  uncapped read. **Fixed** for the Bot API path and post-checked on the
  Telethon paths (§3.5); full incremental streaming remains open (§4.2).

### `formats/`
- Decoders wrap malformed-input parsing in broad `except` returning `[]`/`None`
  — intentional and safe against crashes. Embedded decryption keys/passwords in
  `common/crypto.py` are format constants for decoding known third-party proxy
  formats (with env overrides), not application secrets. Documented in §4.

- New tests: `tests/test_env_expand.py` (9 cases), `tests/test_schema_validators.py`
  (9 cases). The two previously-failing `test_config_loader.py` cases now pass.

### 3.2 Store hardening

- `store/raw_store.py`: `_is_valid_sha256` gate on `get`/`exists`.
- New tests: `tests/test_store_hardening.py` (runtime-reconfiguration + traversal

### 3.3 Orchestrator hardening
- `core/hardened_orchestrator.py`: defensive skip of malformed build results.
- `core/orchestrator.py`: atomic writes for `proxies.txt`, `proxies_b64sub.txt`,

### 3.4 Lint / hygiene

  the test suite) and extended `.gitignore` to cover `*.db` and test scratch dirs.

### 3.5 Later-pass remediations (deeper audit + review feedback)

**Data integrity (CRITICAL)**
- `state/repo.py::prune_old_data` selected raw blobs for deletion using only an
  age + non-pending filter, omitting the active-blob-dependent-record guard that
  `get_processed_hashes` already applies. Because the ingest and record
  timelines legitimately diverge (a file ingested >N days ago but transformed
  recently), prune could delete a blob still referenced by a live `ovpn`/`ehi`/
  `hc` record via `raw_store.prune_by_hashes`, corrupting the next route build
  with no recovery. The guard now covers both the blob set and the `seen_files`
  delete, so the tracking row survives and `prune_orphans` can't finish the job.
  (`tests/test_prune_blob_safety.py`)
- `pipeline/publish.py` raised on any destination failure *before* reaching
  `mark_published`, so `last_hash` never advanced and every destination —
  including ones that already succeeded — was resent the same artifact on every
  run until the failing destination recovered. Success is now recorded before
  the raise; the failure still propagates to the caller.
  (`tests/test_publish_pipeline.py`)

**Concurrency / resource safety**
- `core/session_lease.py`: closed the TOCTOU race where a waiter acting on a
  stale `stat()` could `os.replace` a *live* lease created by another waiter.
  Reclamation is serialized behind an `O_EXCL` `.reap` marker and re-verified
  under it; since holders create leases with `O_EXCL`, no fresh lease can appear
  while the stale file exists, so the reaped inode can't change mid-operation.
  A crashed reaper's marker is force-reclaimed after a bounded TTL.
  (`tests/test_session_lease_reap.py`)
- Introduced `connectors/base.run_sync` and migrated every deprecated
  `get_event_loop()` + `run_until_complete` site (`AsyncSyncIterator.__iter__`,
  the three `telegram_user` sync wrappers, and both orchestrator `run()`
  entrypoints). It uses `asyncio.run` and falls back to a dedicated worker
  thread when a loop is already running — fixing both the Python 3.12+
  breakage and the "event loop is already running" re-entrancy crash, and no
  longer leaking an unclosed loop from `new_event_loop()`.
  (`tests/test_connector_base_iter.py`)
- `telegram_user/connector.__del__` no longer performs network I/O. Per
  CPython's data model, `__del__` runs at arbitrary GC time and during
  interpreter shutdown (where the loop may be closed and globals torn down to
  `None`, and raised exceptions are swallowed). It now releases only the
  in-process session lock — the resource that genuinely leaks and would
  deadlock later acquisitions — leaving socket teardown to the explicit
  `cleanup()` / `cleanup_async()` paths.

**Bounded resources / hardening**
- `formats/opaque_bundle.build`: bounded by `HUNTX_OPAQUE_BUNDLE_MAX_BYTES`
  (default 1 GiB) and `HUNTX_OPAQUE_BUNDLE_MAX_ENTRIES` (default 100 000), and
  now pre-filters on the record's declared size *before* reading a blob, with
  the post-read length check retained as the authoritative fallback.
  Truncation is always logged, never silent. (`tests/test_opaque_bundle_bounds.py`)
- `utils/content_type.py`: the zip-bomb ceiling summed every entry's *declared*
  `file_size`, including entries that are only magic-byte-peeked and never
  opened — a false positive on legitimate archives of many small files.
  Verified against CPython's `zipfile` source that `ZipExtFile.read()` does cap
  a single member's own output at its declared size, but nothing bounds the
  aggregate across a chain of nested archives; the counter now tracks real
  bytes read, shared across recursion. (`tests/test_zip_malware.py`)
- `store/raw_store.py`: `prune_processed` and `prune_by_hashes` built
  destructive `unlink()` paths from repository-returned hashes without the hex
  validation `get`/`exists` already had. Both now reject non-hex values first.
- `utils/atomic.py`: text-mode writes are always UTF-8 (the platform default
  would corrupt or reject the non-ASCII dev-export payloads), and an existing
  target's permission bits are preserved instead of being replaced by the
  umask-derived mode of the temp file.
- Bot API downloader performs a bounded `read(MAX_DOWNLOAD_BYTES + 1)` and
  discards over-cap bodies; both Telethon paths enforce the 25 MB cap on actual
  downloaded bytes in addition to the metadata pre-check.
  (`tests/test_download_cap.py`)
- `config/schema.py`: a string `"0"` bypassed the `v == 0` fast-path (`str != int`
  in Python) and became integer `0`, breaking the documented "zero is absent"
  contract for any zero arriving as text. Now normalized after parsing.
- `core/hardened_orchestrator.py`: a build result missing `route_name` defaulted
  to `"unknown"` and was still submitted to `PublishPipeline.run`, which indexes
  `["route_name"]`/`["artifact_hash"]` directly — a guaranteed `KeyError` in a
  wasted thread-pool slot. Such results are now skipped with an explicit log.

### 3.6 Untrusted-decoder and data-integrity pass

This pass targeted `formats/` — the modules that parse bytes arriving verbatim
from Telegram, where malformed input is the normal case — plus the remaining
state/pipeline integrity items. Every finding was reproduced locally first.

**Crashes and hangs on untrusted input**
- `formats/proxy_uri_validator._validate_ss` **raised `ValueError` instead of
  returning `False`.** When a body has no `@` it is base64-decoded, but the
  decode can succeed and still produce no `@` (`ss://YWJj` → `"abc"`), reaching
  `userinfo, endpoint = body.rsplit("@", 1)`. Callers treat this as a plain bool
  predicate — `npvt._append_uri` does not wrap it — so the exception escaped to
  the transform stage, which marks the **entire source file** failed and
  discards every other valid URI in it. One junk line in a Telegram-sourced
  subscription therefore dropped the whole file. Fixed by re-checking for `@`
  after the base64 fallback.
- `formats/opaque_bundle.build` had **O(n²)** entry-name collision handling: it
  rescanned from `counter=1` on every collision *and* re-ran
  `safe_zip_entry_name` (three regex passes) inside the loop. Easy to trigger,
  because that sanitizer collapses everything outside `[A-Za-z0-9._-]` to `_`,
  so any all-non-ASCII filename maps to one token. Measured on the old code:
  500 collisions 0.5 s, 1500 → 4.3 s, 3000 → 18.1 s — all while holding the
  per-format build lock, stalling that route. Now tracks the next free suffix
  per base name: **18.06 s → 0.20 s at n=3000 (~90×)**, entries still all
  present and distinct.
- `formats/hat.py` decoded with the error handler `"strip"`, which is not
  registered. Handlers resolve lazily, so any `.hat` containing one invalid
  UTF-8 byte raised `LookupError`, which the broad `except Exception` swallowed
  — silently disabling the entire `.tut/.tmt` fallback branch for exactly the
  binary-ish files it exists to serve. Corrected to `"ignore"`.

**Data integrity**
- **Duplicate records in every published artifact.** `seen_files.raw_hash` is
  not unique (only `UNIQUE(source_id, external_id)` is enforced), so identical
  content seen in N allowed sources yields N `seen_files` rows, and both build
  queries fan one record out to N identical rows. The dedup CTE keeps `MAX(id)`,
  but the final join then re-matches every fanned-out row carrying that id.
  Reproduced against a real database: one record + the same hash in two sources
  returned 2 identical rows, so a config reposted in two monitored channels
  shipped twice and inflated the counts. Fixed with `SELECT DISTINCT` in the
  `filtered` CTE of `get_records_for_build` and
  `get_records_for_governed_build`; every selected column comes from `records`,
  so this collapses the fan-out exactly without dropping distinct records.
- **Non-atomic transform flush.** `add_records_batch` and
  `update_file_status_batch` each opened their own connection and committed
  independently, so a crash after records committed but before the files left
  `'pending'` meant the next run re-parsed and re-inserted them — unbounded
  `records` growth with the work repeating every run (build-time dedup hid the
  output impact). Both now accept an optional `conn` (matching the existing
  `get_seen_files_batch` / `record_files_batch` pattern) and
  `TransformPipeline._flush_batch` wraps the pair in one transaction. Verified
  by simulating a mid-transaction crash: records roll back and the file stays
  `'pending'`, so the work is simply retried cleanly.

**Publish/CLI edges**
- `publisher.py` passed an API-supplied `retry_after` straight to `time.sleep()`
  with no ceiling and no type check, unlike `bot/delivery.py` which caps
  FloodWait. A value of 86400 would park a bounded publish worker for 24 h (the
  orchestrator can only *wait* on those futures, never kill them) and a JSON
  string raised `TypeError`. Now validated and capped via
  `HUNTX_PUBLISH_MAX_RETRY_AFTER_SECONDS` (default 60).
- `publisher.py` interpolated `filename` raw into a `Content-Disposition`
  quoted-string, where a `"` or CR/LF could escape the parameter or terminate
  the header and smuggle extra multipart parts. Now routed through
  `safe_component`, which removes those characters by construction.
- `cli/commands/run.py` returned instead of raising on a missing config file,
  exiting 0 so a scheduler read a misconfigured run as success — and
  inconsistently, since every other failure path there raises.
- New `utils/env.py` centralizes the "parse, validate, warn, fall back" pattern
  for environment integers/booleans that was duplicated and inconsistently
  applied (several sites used a bare `int(os.environ[...])` that raises on an
  operator typo).

**Dead code with latent security regressions**
- `HandlersMixin` carried its own `_on_callback` and `_check_rate_limit`, both
  dead because `InteractiveBot` defines them in its class body (verified at
  runtime). The dead `_on_callback` echoed raw exception text to the user and
  the dead `_check_rate_limit` never pruned `_user_cooldowns`; any reordering of
  the base list would have silently activated them. Removed after confirming
  both versions handle an identical set of callback prefixes, so nothing was
  lost. `tests/test_bot_handler_resolution.py` locks the invariant.

**Infrastructure**
- `pr-validation.yml` pinned `actions/checkout` to the **mutable tag** `v7.0.0`
  while every other action in both workflows is SHA-pinned. Now pinned to the
  same SHA `huntx.yml` annotates as v7.0.0 — identical version, immutable ref.
- `pyproject.toml` carried a `[tool.flake8]` section that flake8 **silently
  ignores** (it supports only `setup.cfg`/`tox.ini`/`.flake8`). Verified against
  flake8 7.3.0, which ignored a `max-line-length` set solely in pyproject and
  fell back to the 79-char default. Removed, with `.flake8` documented as the
  single source of truth.
- Audited and found healthy: `requirements.txt` is fully hash-pinned via
  `pip-compile --generate-hashes` (340 hashes) with CI installing under
  `--require-hashes`.

## 4. Known risks (current snapshot — open items only)

Everything remediated during this branch's passes has been moved into §3.5;
what follows is the list of findings that remain **open** as of the branch tip.
Each would change pipeline runtime semantics, depends on maintainer intent, or
carries enough behavior risk that an undertested autonomous rewrite would be
worse than an explicit hand-off.

1. **Hardened thread-pool shutdown** (`hardened_orchestrator.py`): `shutdown(wait=False, cancel_futures=True)` only cancels futures that have *not started*; already-running build/publish threads continue. A run can therefore report `timed_out`/`completed` while publish threads are still delivering to Telegram, making the status unreliable and risking double-publish. A correct fix needs cooperative cancellation plumbed into the pipelines themselves.
2. **Streaming downloads** (`telegram_user/connector.py`, `windowed.py`): the 25 MB cap is enforced on *actual* bytes both before (metadata pre-check) and after `download_media`, so no over-cap data is ever persisted — but `download_media(..., file=bytes)` still buffers the whole payload in memory before the post-check drops it. Telethon's `client.iter_download()` is the supported incremental API and would let the read abort at the cap. Deferred as an async rewrite needing live-API testing this environment can't provide.
3. **Bot-layer concurrency and DoS surface** (`bot/`): `_on_count`/`_on_status`/`_on_protocols` run a synchronous full-table SQLite scan directly on the event loop with no rate-limit gate, so a user can stall the bot for everyone; many outbound paths (`event.respond`, `event.edit`, direct `client.send_message`) bypass the bounded `_send_with_floodwait` helper; and `admin._run_pipeline_blocking` mutates process-global `paths.*` from a worker thread while handlers concurrently read it. Each is a real defect but the cluster is a bot-architecture change (executor offload + uniform throttling + immutable per-run paths), not a local patch.
4. **Delivery session collision** (`cli/main.py::_deliver_updates`): builds a second `InteractiveBot` that opens the same `bot.session` file and authenticates the same bot token as a possibly-live bot process → Telegram 409 + session-file corruption. Needs a distinct session file or delivery through the existing bot/`TelegramPublisher`.
5. **Remaining pipeline data-integrity items.** The record fan-out and the non-atomic transform flush from this list are now **fixed** (§3.6). Still open: `governed_build`'s query-future cache is never invalidated, so a reused instance can serve stale records across cycles; `ingestion_queue._next_rotation_seq` is a racy read-modify-write that can hand two workers the same sequence (breaking fair rotation, not data); `ingest.run` persists the connector's forward cursor even after an early deadline break, which can skip prefetched-but-unflushed messages. Also: `ingestion_queue` has **no attempt ceiling**, so a permanently-failing item retries forever. Note this is *less* severe than first reported — the caller (`optimized_orchestrator.py:286`) already applies exponential backoff capped at 3600 s, so the steady state is ~1 retry/hour, not a spin loop. Adding a ceiling means changing scheduling semantics in the lease/rotation subsystem, which is why it is a hand-off rather than a late-pass edit.
6. **Bot/admin error surface**: `bot/admin.py` sends raw exception text into the admin chat, which can carry config paths and connection details. Should log a sanitized error class/summary instead. (The related `publisher.py` items are fixed — see §3.6. Two claims in that area were investigated and found **not** to be defects: `str(HTTPError)` does not include the URL, so no token leaks that way, and `urllib.error` was in fact reachable via `urllib.request`'s transitive import.)
7. **Format-decoder amplification** (`conf_lines.py`, `npvtsub.py`, `slipnet.py`, `tut/tmt/sks/npv4`): none of these raise — every `parse()` is wrapped in-file and again by the transform stage — but several have no per-file record cap, so one 25 MB message can expand into hundreds of thousands of DB rows, and the `tut/tmt/sks/npv4` deep-parse path stores whole-file text (plus its decrypted copy) in a single row. Separately, `npvtsub.parse` does not call `validate_proxy_uri` where its sibling `npvt.parse` does, so unvalidated URIs reach the published subscription artifact. These are throughput/quality issues rather than crashes; each cap is a product decision about what to drop.
8. **Embedded format keys/passwords** in `common/crypto.py`, plus **AES-ECB** and **PBKDF2 at 1 000 iterations**. Confirmed *format-intrinsic*: the passwords are the originating third-party apps' fixed constants, the ECB mode matches netmod's own implementation, and the iteration count must match the encrypting app's default — none can change without breaking decode, so OWASP's ≥600 000-iteration guidance does not apply (these protect no HuntX-chosen secret). Accepted as documented public constants, env-overridable, not rotatable secrets. What *is* safely improvable: the AES-GCM `iv`/tag lengths are taken from attacker-controlled input with no length validation (an 8- or 128-byte IV is silently accepted instead of the format's 12), and several `b64decode` calls omit `validate=True`, so malformed input silently maps many distinct payloads onto the same key material.
9. **Repo weight**: `data_archive/` (~800 MB), `outputs_dev/` (~123 MB), `outputs/` (~32 MB) are tracked runtime artifacts. Consider Releases/LFS and untracking — untouched here because discarding ~1 GB of committed data is a maintainer decision.
10. **`pyaes` build** fails under modern setuptools; the pinned `pyaes==1.6.1` sdist needs `setuptools<60` to build a wheel. Consider a maintained fork or a documented constraint in the dev setup.
11. **`upload-artifact` version skew**: `pr-validation.yml` pins a v6 SHA while `huntx.yml` uses v7.0.1. Aligning is a major bump (v7 moved to ESM/Node 24) that dependabot PR #57 already proposes, so it belongs there.
12. **Docstring coverage** is ~23% against an 80% target (flagged by the PR's automated pre-merge check). Not a correctness issue; noted so it is a deliberate choice rather than an oversight.
